Snapshot taken 10 September 2026. Verified against live sources, not against documentation: the routine list from the Claude API, registry from estate-db, wrangler d1 list, and a sweep of every wrangler.toml on disk. A status with no date beside it is not a fact, so this page carries one. It is hand-assembled today and should be generated; see the note at the bottom.

1Naming

One scheme, used everywhere from here on. Every agent and worker is <owner>:<role>, where the owner is the property when a thing serves exactly one, and the entity when it serves several or none. So Patriot's finder is patriot:scouty and RecordStops' is recordstops:scouty, never patriot-scouty and never a bare Scouty. That key is the registry primary key, the URL of its instructions, and the name it must use in every report it writes. Anything running under a different name is unregistered, which is a defect rather than a style.

3How mail actually moves

Nothing polls for mail. Cloudflare pushes each message into a Worker the moment it arrives, which is why neither email worker has a schedule and why they were easy to miss.

INBOUND, what fills the Inbox page

  someone emails hello@patriot.directory  or  hello@recordstops.com
        |
        v
  Cloudflare Email Routing rule on that domain
        |
        v
  Worker machine-email-intake   (directories:email-intake)
    picks the database by recipient domain, checks SPF/DKIM/DMARC,
    detects auto-replies and opt-outs, matches a reply to the message
    that caused it, then writes one row
        |
        v
  inbox table in patriot_directory_db  or  recordstops-db
        |
        +---> the desk reads it at /api/inbox  ->  Inbox page
        |
        +---> the Mailroom reads it at /api/automation/inbox?status=new
              and turns each message into typed work

OUTBOUND, and how a bounce finds its way home

  the desk fires a lever  ->  outbox row claimed  ->  Cloudflare Email Service
        |
        v
  Email Service publishes a delivery event to the mail-events queue
        |
        v
  Worker machine-mail-events   (directories:mail-events)
    sole consumer, batches of 10, three tries then a dead letter queue
        |
        v
  outbox status moves to delivered or bounced, and a hard bounce
  adds the address to suppression so nothing mails it again

One Worker serves both directories in each direction. That is deliberate: the routing table is data, the brand separation is the database it selects, and a second Worker per directory would be two copies of the same parser drifting apart. The agents are per property; the plumbing is not.

6What is wrong right now

Findings from this sweep, worst first. Everything here was verified against a live system today, not inferred from a document.

1. A retired worker is still deployed and still on a cron

recordstops-newsletter was removed from the repo today, which undeployed nothing. It is still live in Cloudflare, last deployed 23 June, and still carries crons = ["0 13 * * SAT"]. It sends from the apex hello@recordstops.com, which the machine forbids because the apex carries the reputation every listing page depends on, and its unsubscribe links cannot be parsed by the site that receives them.

Fix: delete the Worker, or disable its trigger. Deleting source is not deleting a deployment, and that is the general lesson worth keeping.

2. Nine things run that the estate does not know about

Everything tagged "runs unregistered" above. Watchy cannot see them, none of them reports coverage, and if one silently stopped tomorrow nothing anywhere would say so. That is the first law failing quietly: nothing runs unless it is in the registry, and nine things do.

3. Three routines write to the client CRM

ascend:sparky, ascend:wordy and ascend:clippy all write to ascend-db, a client-facing production database holding real client records. The estate already has the replacement: estate-db.drafts plus a rejections endpoint, which is what Blogy already uses. content_drafts in the CRM duplicates it.

4. Wordy reads a table that was retired

ascend:wordy takes part of its weekly input from session_log, retired on 7 September. Nothing has written to it since. It will not fail; it will produce something from an empty input every Saturday, which is worse than failing, because a failure is visible.

5. Two Patriot routines call the wrong hostname

patriot:mailroom and patriot:tidy both name patriot-directory.pages.dev in their prompts, while the spec they fetch now gives them patriot.directory. The prompt tells them, in its own words, to use the base the spec gives them and never a hostname they remember, and then hands them one. Both hosts answer today, so nothing is broken. pages.dev is a deployment artifact and the apex is the brand.

6. RecordStops' database is bound by the wrong name

wrangler.toml declares database_name = "DB", the binding name pasted into the name field. The id is correct, so it works, but any tool that resolves by name will miss it. The binding also exists only under [env.production], so a local dev run gets no database at all and every route throws at request time.

The boundary that matters is holding

The desk binds jbmangum-desk and estate-db and does not bind ascend-db. Exactly one deployable binds the client CRM: ascend-api. No client name, address or dollar amount has crossed into the estate or the desk.

How this was built, and how it should be built. Every row came from a live source today: the Claude routine API, estate-db.registry, wrangler d1 list, and a sweep of every wrangler.toml on disk. But it is hand-assembled, and the estate's own first law says a registry that is hand-maintained will drift, because every hand-maintained roster in this operation has drifted, usually within three weeks.

The honest end state is a page generated from registry, agent_runs and a config sweep, served by the estate, with this snapshot as the shape to aim at. Until then, treat this as true on 10 September 2026 and check the live sources before acting on anything here.
