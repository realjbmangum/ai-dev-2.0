Three pages on the desk

Estate, Inbox, Log. What each one shows, what every control does, and what has to be built to serve it. Every number below was read from a live database today.

Why this document exists

There was no spec. The earlier sketch was a mockup, it was written before Mailroom existed, and it is now wrong in the ways that matter: it says no mail can arrive, that the inbox is empty, and that the zone has no MX record. All three were true that morning and none is true now. Building from it would have meant building from a picture of a system that no longer exists.

The reference

What we are copying from AgentWork, and what we are not

The shape is right: a row of counts across the top, a roster of workers with what each is doing, an activity feed beside it, and detail below. Four things carry over directly.

From AgentWorkHere
Stat cards with a delta against the last periodSame, but the period is a day, not fifteen minutes. Nothing here moves fast enough for a 15-minute window to say anything.
Live worker table: who, doing what, statusSame. Agent, entity, last run, what it covered, when it is next expected.
Real-time activity feedSame, fed from the work log. This is the strongest borrowed idea: it makes an invisible fleet legible in one glance.
System status and capacity in the cornerSame, as the switches: fleet on, dry run, drafts only.
Three things from that screenshot are deliberately not copied

"Success Rate 96.7%." The estate's second law is coverage, not success, and it was written after a cron returned success every Monday for six weeks while covering 3 of 16 sites. A success percentage is exactly the number that hid it. What replaces it is coverage: 13 of 15, with the gap visible.

Live progress bars. AgentWork's agents work continuously, so 72% means something. These agents wake, work, report and stop. A progress bar would be decoration animating a thing that is not happening.

Avg completion time. Nobody is waiting on these. A run taking four minutes rather than two is not information, and putting it on screen makes it look like it should be.

What every control does

  • Approve / Reject on a candidate posts to the directory's candidates route and moves to the next one. Keyboard a and x, because seventeen decisions with a mouse is a chore and seventeen with two keys is a minute. Reject asks for a reason from the closed list and nothing else: wrong voice, already said, not true, too thin, not now, other.
  • Run now fires that agent's routine immediately. Mute suppresses one finding for 24 hours and says so on its face, because a mute with no expiry is how an alarm dies quietly.
  • The switches write to estate_control and nothing else. No deploy, no code change. That is the whole point of that table.
One thing the first version should get right

The open finding on this page today says "Tidy reported success while covering 13 of 15." That was correct when it opened and it is now noise: 13 of 15 is a good run, the two gaps are websites that were down. If the page ships with that sitting on it permanently, the "wrong right now" count stops meaning anything within a week.

So Mute has to exist in version one, not version two, and it has to be a first-class control rather than a nicety. A dashboard nobody can quiet is a dashboard nobody reads.

The outbound half is honest about being unbuilt

Reply, Resolve, and the whole "going out" section have no backend. Cloudflare Email Routing receives and forwards; it cannot originate mail to arbitrary recipients, and Cloudflare's sending product is transactional-only by their own documentation. Outbound needs SendGrid, which already exists on this account and is wired to nothing here.

Version one shows those controls greyed with "not built" rather than hiding them. A dashboard that hides the unfinished half quietly teaches you the system does less than it does.

Undo is the point

Every reversible change already stores its before and after, written by the endpoint rather than by the agent, so it cannot be forgotten. Undo posts the before_json back through the same enrichment route with overwrite: true, and logs the reversal as its own act. It never deletes the original row. The history of a mistake is not itself a mistake.

A row gets an Undo button only when before_json is present. Everything else — a check that changed nothing, a ticket opened, mail received — shows none, because there is nothing to put back.

Four

What has to be built to serve it

How the desk reaches a directory, and why not directly

The desk Worker binds jbmangum-desk and will now also bind estate-db. It does not bind any directory's database, and should not.

  • One writer per store. Directory Machine's own rule. A second system writing that database is how two systems end up disagreeing about the same row.
  • It does not scale. Ten directories would mean ten bindings on a page that is supposed to work by adding a row to a picker.

So the desk Worker calls each directory's automation API over HTTPS with a bearer token held as a Cloudflare secret, and proxies it. The token never reaches the browser. That API already exists, is already rate limited, and is the thing it was built for.

browser  ->  desk Worker  ->  estate-db          (agents, runs, findings, switches)
                         ->  patriot API        (candidates, mail, tickets, work log)
                         ->  recordstops API    (later, same shape)
The boundary that must not move

The desk never binds ascend-db, and neither database it does bind may hold a client name, an email address or a dollar amount. Ascend's work reaches this desk as a pointer — "3 leads quiet 9+ days, open the CRM" — never as a payload.

This already had to be enforced once today. A run report had copied a business's contact address into the estate database; it was scrubbed and the upstream spec corrected. The Inbox page displays real addresses, and it must read them live from the directory rather than caching them anywhere.

Routes that exist

Everything the Estate page and the Log page need is already live: candidates, work, health, businesses, plus the estate's registry, runs, findings and state.

"Run now" may not be buildable as drawn

Firing a routine on demand needs the claude.ai routine API, which authenticates with an interactive OAuth session. A Cloudflare Worker has no such session. This is the same constraint that made the watcher a Worker cron rather than a routine in the first place.

So the button is either dropped from version one, or it becomes a link that opens the routine on claude.ai. Recommend the link. An honest link beats a button that fails, and it costs nothing.

Five

Build order
  1. Estate, read only. Counts, the team table, findings, the activity feed. Every source already exists, so this is the fastest path to seeing the whole fleet at once.
  2. The 17 candidates, with keys. Turns a readout into a control on day one, and clears a queue that has been waiting four days behind a screen that did not exist.
  3. Switches, and Mute. Both write. Mute ships with version one for the reason given above.
  4. Log, read only, then Undo. Reading is easy; Undo needs the revert lever built first.
  5. Inbox, read only. Inbound is real today. Outbound shows as "not built" until it is.

Steps 1 to 3 are the ones worth doing in one sitting. They are the difference between a fleet you are told about and a fleet you can see and stop.
