Four

What is still wrong

Ranked by consequence, excluding the items in section one.

  1. The watcher cannot detect its own death.

    If the estate-api cron stops, last_run_at freezes, no query runs, and /api/state keeps serving whatever all_clear last was. Moving the watcher off the routine rail fixed the deletion failure that killed Tally and Chiefy. It does not fix the silence failure. There is no external dead man's switch. This is the exact failure mode the repo exists to eliminate, still present in the one component that eliminates it for everything else.

  2. The registry is hand-edited and already drifting, one day old.

    Law 1 says the registry is generated. It is not: the seed is 9.4 KB of hand-authored SQL with no generator. Two notes are already wrong. crownandcompass:wordy still says "blocked until brand-standards.md is corrected" when that was corrected yesterday, and estate:loggy still describes writing to ascend-db.session_log, which was explicitly overturned. This is what killed ROSTER.md, reproduced in a new store within a day.

  3. The served spec's git SHA is a false claim, structurally.

    Proven today by a 23-second race with a clean tree: specs.synced_at is 17:28:01 and the commit is 17:28:24, so D1 serves post-commit content stamped with the previous SHA. --check cannot catch it, because it compares D1 against the working tree rather than against a commit.

  4. confirmed_at is null on all twenty rows and no route writes it.

    The column exists, queries select it, nothing sets it, no finding flags it. By the schema's own rule, borrowed from ascend-db.entities, every row in the registry currently reads as unconfirmed rather than as fact.

  5. Rules with nothing enforcing them.

    Hard rule 4, no client data, has zero enforcement and agent free-text lands in four columns with only length caps. Law 4, ground every claim, is prose, and source_note is nullable with no CHECK. Hard rule 6, never hardcode a limit that lives in estate_control, is violated by the rate limiter itself. Hard rule 8, no general passthrough: the README says eight routes, thirteen exist.

  6. The rejection trigger has a hole.

    trg_drafts_rejection_needs_reason fires only BEFORE UPDATE OF status. An INSERT setting status='rejected' with a null reason passes both the trigger and the CHECK. The stated reason for having a trigger at all was that something other than the desk will eventually write that table, which is exactly the case the hole is open for.

  7. Patriot Directory still has three live front doors, and an agent now runs through one.

    All three answer /api/automation/health with 401 rather than 404. Two repos deploy against one production database, and the stale one can redeploy on any push. Flagged on 5 September as fix-regardless; the first field agent shipped through it unresolved.

  8. No cloud routine has ever opened a pull request.

    allowed_push_branches is empty on every routine and none carries a GitHub connector. Voicey opens PRs, but Voicey is a cockpit task on your Mac with a real checkout, so it proves nothing about the cloud rail. Blogy, Wordy and the archived Thursday writer all depend on a mechanism nobody has demonstrated. The Thursday writer's next scheduled fire is 10 September.

  9. The drafts table has no reader.

    The queue moved into estate-db.drafts and is served as JSON behind a token. Nothing else reads it. The first draft any role produces will land in a store with no interface in front of it.

  10. The first finding cannot close before Tuesday.

    An undercovered finding closes only when a fresh run reports actual >= expected. Tidy's cadence is weekly. So all_clear stays false for five days, and nothing can say why. The contract was meant to be "silence means healthy". Right now it is a stuck light in a locked room.

  11. The README is stale in the estate's own signature way.

    Five finding kinds, eight routes. Six and thirteen exist. Nothing checks it, and it is the copy a next session actually opens.

Five

The rules, and where they came from

You wrote these. They are here for the next reader, and because three of them are currently failing their own test.

"If it needs a human to remember it, it has already failed."
From ROSTER.md, and the sharpest test written anywhere in this estate.

It currently fails against sync-specs.mjs, which a human must run; against the registry, which a human hand-seeded; and against the README, which a human must notice is wrong.

The five laws

  • Nothing runs unless it is in the registry, and the registry is generated. Half true. Registration is enforced; generation is not built.
  • Every run reports coverage, not success. Enforced in the route: a report without expected and actual is refused, and no_unit: true makes omission a decision.
  • Agents propose, humans dispose, and the gate is a status column. Enforced. An agent cannot read status from a request body, and only admin may PATCH one.
  • Ground every claim, or produce nothing. Prose only. Nothing enforces it.
  • Instructions are served, versioned and drift-checked, never embedded. Built today, with the SHA caveat above.

The two ideas worth keeping from before

"D1 holds what a machine queries. Git holds what a human writes and reads."
The word "log" was doing two jobs. Telemetry is machine data, queried constantly. Narrative is writing, read by people. Putting either in the other's home is what made this feel hard.
Five to ten minutes is roughly 10 to 15 decisions. That allows exactly one drafting role to run daily. Everything else is weekly and lands on its own day. A second daily queue breaches the budget, and a breached budget is how Clippy sat at 0 approved out of 25 for a month.
The only place in the old documents where a constraint was derived from evidence rather than asserted.
