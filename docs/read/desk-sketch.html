Every number in this sketch is real and was read from a live database today. Nothing here is invented sample data, because the point is to show you what the page would say this morning.

The one rule this sketch obeys

Your desk's own brief says "success is time-to-close, so anything that increases dwell time is a bug" and "it is built to be emptied, not looked at." A live-status dashboard is the opposite of that. So the fleet page is not a monitoring screen with activity feeds and sparklines. It is a page that is mostly empty when things are fine, and that only shows you something when something needs you.

Notice what is missing from that page

Connectors: the one thing you asked for that has no data behind it

You asked to see connectors. I checked all four databases. Nothing records which connectors an agent holds, or which tools it is allowed. That lives only in Claude's own routine settings, and reading it needs a login that a background service cannot have.

It matters because it is where a real risk sits. Three of your older routines each carry eight connectors they do not need, including mail that can send and your accounting system. Tidy carries none, deliberately.

Two ways to get it on the page. Either I record each agent's connectors as I build it, which is accurate from now on and blind to the old ones, or you run a one-line command occasionally that refreshes the whole picture. I would do both: record going forward, refresh on demand.

Four

Two things worth knowing before you say yes
The fleet page is mostly empty because most of the fleet does not exist

Three agents have ever run. Seventeen more are registered and have never fired, because they are not built yet. The page will be honest about that, and honestly it will look thin for a while. That is the real state, not a rendering problem.

Your morning bots are invisible to all of this

Your four grok bots have produced 34 runs and fired again this morning. The estate has never heard of any of them, and the desk records them somewhere else entirely. Two systems tracking the same agents and disagreeing is the exact problem we started this to end, and it has quietly reappeared.

Worth fixing in the same pass, and it is small: they already write to the desk, so the desk can pass that on.

What I would build, in order

  1. The Fleet page, read-only, with the counts and the team table. Proves the wiring.
  2. The 17 candidates with working buttons. This is the only real queue you have, and it turns the page from a readout into a control on day one.
  3. The switches, so you can stop the fleet from your phone instead of from a database.
  4. The log with undo.
  5. Connectors, recorded as each new agent is built and refreshed on demand.

One and two together are the useful half. Three onwards can follow whenever.
