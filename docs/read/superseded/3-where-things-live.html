How the estate actually works

Where every piece of state lives, why it lives there, and which of the two stores is the source of truth for what.

One

Two stores, and they hold different kinds of thing

This is the question underneath all the others. There are exactly two places state lives, and mixing them up is what made the last three weeks confusing.

Neither is a copy of the other. They hold different things, so they cannot disagree.
The one-line rule

D1 holds what a machine queries. Git holds what a human writes and reads. A copy is a second source of truth and the two will always eventually disagree, which is your own schema-bones-and-vertical-flesh rule. So nothing is copied. The split is by kind, not by convenience.

Two

Why not put everything in GitHub

Your instinct is right that git should carry more than it currently does. But there is a hard constraint, and you have already been bitten by it twice.

A cloud routine cannot read a private repo

Sixty-four of your sixty-seven repos are private. allowed_push_branches is [] on every routine you have, and not one of them carries a GitHub connector.

This already cost you real output. Your own 5 September review put it plainly: "All your repos are private. I checked. So grok cannot see a single thing you build, which is why 'one I-built draft' has never had a source and why brackets kept creeping in." And in August, ascend-systems moved every agent doc off git and into D1 for exactly this reason. That migration's own comment says it "blocked making the repo private, since it was unclear whether the Routine runner clones authenticated."

Three further costs, all real but smaller:

CostWhat it means in practice
Querying is grep"Show me everything that went quiet in the last 30 days" is one SQL line against D1 and a scripting problem against git. Watchy runs that query 96 times a day.
Writes collideTwo agents appending to one log file on the same day is a merge conflict. Two rows in D1 is nothing.
Commits trigger buildsSeveral of your repos auto-deploy on push. A telemetry commit every 15 minutes would rebuild the site every 15 minutes.

And why not put everything in D1

Because you already decided otherwise, correctly. On 29 August you retired ship_logs with the reasoning that the publishable record is the git history, settling a contradiction that had been sitting in your rules for months. A narrative log in a database is a log nobody reads, cannot diff, and cannot review in a PR.

So the split is not a compromise. It is the correct answer.

The word "log" was doing two jobs. Telemetry (did it fire, expected versus actual, is anything overdue) is machine data, queried constantly, and belongs in D1. Narrative (what we did, what we decided, what broke and why) is writing, read by people, and belongs in git. Putting either in the other's home is what has been making this feel hard.

Four

Loggy, corrected
You caught a real error

I had Loggy writing to ascend-db.session_log. That is Ascend Systems' client-facing CRM database. Putting the estate-wide work log inside one child entity's database is backwards, and it is the same category error your own desk README already forbids: "This Worker binds DB to jbmangum-desk and nothing else. It never binds ascend-db."

I inherited it from the existing convention without questioning it. The convention is wrong, not just my application of it.

What Loggy does instead

The entry

git · the entity's own repo
  • One markdown file per day, per project touched.
  • Written by a GitHub Action, so no credential leaves Cloudflare.
  • Diffable, reviewable, and already the publishable record.
  • Source of truth.

The index

D1 · estate-db
  • Date, project, commit SHA, one-line summary.
  • Enough to answer "which projects went quiet" in SQL.
  • Never the prose. The prose is in git.
  • A pointer, not a copy.

Loggy exists because the rule is mandatory, manual, and mostly not happening. Across your entire filesystem, only three repos have ever produced a session log row, and a headless routine cannot produce one at all, because writing one today means hand-authoring SQL and running wrangler.

Six

Everything, on one page
Guides and templates flow left from git into D1 on merge, so agents read a served copy and you edit a reviewable file.

Reading the map in one paragraph

Every agent wakes, fetches its instructions from estate-api, does its work, and posts what it did. That report lands in D1 immediately, where Watchy can query it. Nightly, the narrative half is committed to git by a GitHub Action, which is the only thing in the system with repo write access. You edit voice guides and role templates as files in each entity's repo, and merging pushes them into D1 so agents read exactly what shipped. Nothing an agent produces reaches anyone: it lands on the desk, and you spend five to ten minutes emptying it.

The live registry is estate-db.registry. This page is a reading of a design, not of the database, and it will go stale the moment the two disagree. Where they disagree, the database is right.
